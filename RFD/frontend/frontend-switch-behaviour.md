## What the switch means in the current screen

In the supplied screenshot, **Infrastructure** in the upper left is the current project name (`app/src/views/private/components/project-info.vue` reads `serverStore.info.project.project_name`). `Tracking`, `Test`, `Aaa`, and `Sre` below are collection **folders** in the current single schema. They are not namespaces yet. Virtual namespaces are created on demand under the main namespace; the screenshot's folders are examples, not a fixed namespace list. After this feature, the active namespace needs an explicit, persistent label/switcher. In a populated `Tracking` virtual namespace, Content shows **only Tracking's folders and collections**: `Test`, `AAA` and other areas do not appear in its sidebar, search, bookmarks or rows. Switching to another populated namespace clears Tracking navigation and table rows before the target appears. A shared project name may remain “Infrastructure”; it must not be mistaken for the selected namespace. Creating a virtual namespace alone does not copy a same-named folder or its data into it.

The RFD's security invariant is stronger than changing the sidebar: each protected CMS data request has one active namespace context, and namespace-owned data/schema/roles/flows must never appear in another context. Shared users, sessions, files/folders, activity/revisions and optionally settings remain shared **storage**; their visibility or filtering still follows the RFD's access rules. A collection path and primary key, role name, bookmark ID or dashboard ID can mean something different in another namespace. File IDs are globally shared under the current plan. The UI must not briefly display old namespace data under a new namespace label, and server-side authorization remains the isolation boundary.

This is a **prototype with no data migration**. The spec describes how the frontend must behave against provisioned namespace copies; it does not require moving the existing CMS data. A user may hold roles in several namespaces, but the app evaluates **only the active namespace's role** at a time. It must not merge permissions or show a combined cross-area view.

The explicit table split controls ownership: users, roles, permissions, sessions, files/folders, activity/revisions and migrations have shared storage, while collections/fields/relations, flows/operations/webhooks, presets/dashboards/panels/notifications/shares belong to a namespace schema. Shared roles/permissions/audit records still require namespace scoping. The frontend consumes the resolved API contract rather than inferring visibility from storage placement. File visibility remains unresolved (D07 in the implementation plan).

## State ownership rule

| State | Switch treatment |
| --- | --- |
| Session and shared user identity | Keep login/cookie and user ID. Replace the access token and active role. Do not call `logout()`; it deletes auth state and redirects to login. |
| Namespace data and access | Clear/reload user **effective role**, permissions, metadata, items, presets, flows, dashboards, notifications, navigation and scoped extension state. Treat current role as part of the request context, even if the shared `directus_users.role` column is null. |
| Platform namespace registry and authority | Namespace-management page data belongs to the control plane. A content switch does not re-scope the registry or grant platform access to a child admin. Refresh registry after creation and refresh Global Admin authority on re-authorization; clear the page if that authority is lost. |
| Personal UI preferences | Keep theme, language, sidebar width, and shell open/closed preference if desired. Key “last collection” and any collection-specific preference by `(user, namespace)` or clear it. |
| Pending edits and writes | Ask about unsaved changes **before** switching; retain drafts until target commit. Stop new writes/debounced autosaves; drain admitted writes/uploads in their original context. A failed or unknown write result keeps the user in source pending reconciliation. Cancel queued reads; never silently cancel/replay a submitted mutation in target. |
| Browser URL | Include a namespace identifier in the **admin UI URL** for refresh/deep links. API paths such as `/items/<collection>` remain unchanged. Do not put access tokens in the admin URL. |

## Admin and membership behaviour

- A main-namespace admin automatically has effective admin access in every child virtual namespace, including a child created later. The switcher includes every child for that admin without requiring a child membership row. Other users see only namespaces they are authorized to enter; the main namespace appears only if they have main access. Effective inherited admin access comes from the main-namespace admin role, not a separate `is_global_admin` flag. A lower child role must not downgrade that access; losing main admin status must remove inherited access on refresh/re-authorization.
- **Global Admin is the only administrative role whose authority crosses boundaries.** A user with several ordinary memberships still has separate local roles; permissions are never combined. The previously agreed main-admin inheritance supplies Global Admin authority and remains effective while viewing a child.
- **Virtual namespace management is a separate platform page for Global Admins.** It lists virtual namespaces, offers creation, reports provisioning status, and allows entry into a ready namespace. Creation is a platform operation; neither its authorization nor its destination is inferred from the selected content namespace. The page and create endpoint require an explicit platform capability such as `platform.create_namespace`, never merely the active role's `admin_access`. The UI needs name/identifier validation, duplicate/error handling and provisioning/loading states. Creation refreshes the platform list and switcher without implicitly changing the active namespace; **Enter namespace** uses the normal guarded switch transaction and safe empty landing page. Exact route and endpoint names remain contract decisions. The backend returns a stable ID and readiness status.
- User creation and the full shared-user directory belong to the main namespace. In a child, the Users/membership page lists **only members of that child**, with their local roles. A child admin can create/edit local roles and use **Add existing user** to search the shared directory, choose an existing user, and assign one of the active namespace's roles. This is a scoped selection lookup, not a page listing every main-namespace user. Handle duplicate membership, inactive users and search errors without exposing unrelated directory pages. The child admin cannot edit shared user details, create users or create namespaces. After assignment, refresh the active member list and role counts. Inherited main admins may not have a child membership row, so explain that access separately rather than silently treating them as ordinary child members.
- A child admin sees all content in their child, subject to the server's effective admin policy. Switching away removes that admin capability and all child-specific management controls. The backend must enforce every boundary independently of hidden UI controls.
- **Unassign user** removes only the active namespace's membership/role assignment. It does not delete the shared user, edit their global profile or change memberships elsewhere, and cannot revoke inherited Global Admin authority. Refresh local members/role counts and invalidate the removed local access; if the current user loses access through self-unassignment, leave the protected view and offer an authorized namespace. Reject foreign-namespace role IDs and expose no global-profile fields in the local assignment editor.

## Required switch lifecycle

1. **Preflight:** validate target/readiness, serialize switches and ask once about dirty state, including a query-only namespace change. Stay preserves source. Discard retains drafts until successful commit.
2. **Quiesce:** disable new namespace actions; pause polling/autosave/tracking, cancel reads and drain admitted writes/uploads in source. Failed/unknown writes keep the user in source. Resume producers on a rejected switch.
3. **Mint:** obtain a target token in the auth control lane. Denial retains source. Ambiguous network failure uses the agreed reconciliation contract (D02); do not assume source validity after server-side effects.
4. **Commit:** unmount source before showing target context; install matching target token/namespace/expiry, advance epoch, reset scoped state/routes and replace the URL with a static target loading route. Retain intended destination separately; do not run protected route side effects yet.
5. **Hydrate:** load required access/permissions/fields/collections/relations and destination resources, then permitted modules. Required failure stays blocked in target with Retry/Choose namespace; optional-module failure closes that module. Cancel/settle sibling reads so partial failure cannot become false success.
6. **Route/ready:** validate target destination and replace the loading route with it, reconnect target polling, restore focus and enable actions. Returning to source after commit is another switch.

`hydrate.ts` marks hydrated after caught failure and skips dehydrate when that flag is false. `userStore.hydrate()` catches internally; flows/Insights also swallow errors. Required reads must return checked results/throw, and partial reset must always run. The [shared implementation plan](frontend-implementation-plan.md#6-one-switch-transaction-for-every-entry-point) defines transitions/transport rules; [C2's reset checklist](C2-switch-handling.md#reset-and-exposed-surface-checklist) assigns concrete cleanup work.

For C3, `?ns=<stable-id>` is the frontend recommendation pending D13 agreement. Intentional picker switches discard source item/bookmark/query context; explicit target deep links preserve their intent only after target validation. Same-namespace links preserve unrelated queries. Bootstrap, Back/Forward, login/SSO/TFA and coordinator navigation-loop rules are defined in [URL and route rules](frontend-implementation-plan.md#8-url-and-route-rules). Public share context is separate from personal namespace authentication. Platform routes require global authority rather than the current child role.

## Acceptance scenarios for the eventual implementation

- In a populated Tracking virtual namespace, the Content tree, collection search, lists and bookmarks contain only Tracking content; `Test`, `AAA` and other current-screenshot folders are absent. This comes from scoped metadata/API responses, not a client-only folder filter.
- Switch Tracking → another populated namespace from a Tracking list: old rows, sidebar folders, bookmark, selection, filters and manual actions disappear before the target renders; auth session remains valid.
- Put the **same collection name and item key** in two provisioned namespaces: each URL/render and API request shows only its own schema/data, including after Back/Forward and hard reload.
- Type a filter that triggers preset autosave, then switch immediately: the delayed save cannot write to the target namespace; target preset remains untouched.
- Start a slow read, an upload/export, and a mutation, then switch: stale read cannot repaint target; write stays in source context; job ownership and user feedback remain clear.
- Edit an item or flow without saving, then switch: user can stay or discard; no token/context change occurs before that decision.
- Open two provisioned namespaces in separate tabs and let both tokens refresh: each tab remains in its own namespace and URL.
- Revoke membership while a tab is open: the next action fails safely, clears protected view state, and offers a valid namespace without misreporting the login session as expired.
- A Global Admin opens the separate namespace-management page while viewing Tracking, creates a virtual namespace through platform authority, and sees provisioning status. Tracking remains active until they choose **Enter namespace**; then the new namespace opens with inherited admin rights without a child membership row. A child admin receives a denial for both a guessed management-page URL and the create endpoint.
- Remove a main admin grant while that user has child tabs open: inherited controls and access disappear after authorization refresh; a lower child role does not override an active main-admin grant.
- A child admin sees all content and manages roles only in their child. Its membership page contains only child members; **Add existing user** finds a shared user and assigns a local role. No shared-user creation/editor or other namespace members are shown. The main namespace retains user creation and the full directory.
- A child admin unassigns a user's local role: the membership disappears and local access is revoked, while the global account/profile and other namespace roles remain intact. A request attempting to edit global-profile fields or assign a role from another namespace fails server authorization. If backend policy permits self-unassignment, it leaves protected content safely; otherwise the denial preserves membership.
- Compare child admin, ordinary member and main admin: only allowed namespaces and admin actions appear; direct API enforcement agrees with UI. A main admin retains inherited admin access to future children.
- Open a share link while signed into another namespace or signed out: it resolves only the intended share/namespace and cannot expose unrelated content.
- Switch to a newly created empty namespace: show its name and an empty Content state, with no leftover collections from the source namespace.

No source implementation, migration or tests were run for this analysis. The deployment/reference database is not modified.
