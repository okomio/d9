# Backend-aligned frontend delivery plan

Status: **planning only**. Backend source inventory reviewed against `hackathon` at `ccdb4d737` on 2026-10-14; the product contract below includes the 2026-10-21 user-profile clarification. The inventory is historical, not a claim about the current branch or runtime. This document is a plan, not evidence of a working frontend or a tested backend. It supersedes earlier mock-screen assumptions where they conflict with the product direction below. [C1](C1-namespace-switcher.md), [C5](C5-membership-admin.md), [C7](C7-global-admin-page.md) and the [switch specification](frontend-switch-behaviour.md) remain the detailed block and surface checklists.

## Product contract

The selected virtual namespace supplies the data and effective permissions for the **existing Directus shell**: Content, User Directory, File Library, Documentation where installed, Settings, notifications/profile, and the existing list/item sidebars and tools. Keep Directus layouts, search, filters, presets, selection, auto refresh, import/export, archive, activity and actions. A switch must rebind or clear each surface according to the switch specification; a hidden sidebar alone is not isolation.

- Show the parent project name (for example **Infrastructure**) and active area (for example **Tracking**) as two clear levels in the upper-left header. Open the chooser from a persistent button above Notifications in the left rail, as decided in [switcher-review-decision.md](switcher-review-decision.md). Use stable IDs internally. The backend's `main` registry entry can remain for compatibility; do not label it “Main Virtual Namespace” in the product. Decide separately whether Global Admin needs a visible legacy/main workspace option during migration.
- Users without an enterable virtual namespace reach a static no-access/chooser state. They must not see fallback main content while the choice is unresolved. Users with one eligible child can land there automatically; a saved default among multiple eligible children takes precedence once the backend supports it. Global Admin can enter ready children without a membership.
- The normal User Directory inside a child keeps the Directus directory appearance and tools where authorized, but reads only **that child's members**. Its `+` action is **Add existing user**, followed by one role from this child. A local admin can change/remove that local assignment and manage local roles, schema and flows; cannot create/invite an account or edit the shared profile. Multiple child memberships per account are allowed, one local role per child.
- Add a separate **Global Administration** module to the left vertical rail, visible only to inherited Global Admins. Its **Users** view is the shared account directory with namespace/role filters and global Create User/Invite User. Its **Virtual Namespaces** view is a Directus-style selectable list with readiness/status, a create action and the usual contextual actions where the backend permits them. Do not place Create Namespace in the Users sidebar. Creating a namespace never switches the current content context; entering one is explicit.
- Role creation happens after entering the child. A local administrator assigns existing users only in that child. A Global Admin can also edit an existing user's memberships from the native Global Admin user profile through a two-column Namespace Access relation list (Virtual Namespace, Role) with **Add Existing** only. Global account creation/invitation may attach zero or several initial `(namespace_id, role_id)` assignments, each role loaded from its selected namespace, once a coherent backend operation exists. A namespace filter in Global Users does not change the active content namespace.
- Clicking the avatar opens the signed-in user's native editable profile directly, including in a child namespace; permitted personal-field writes need an explicit backend self-service contract. The profile offers a server-validated **Default Virtual Namespace** preference. A saved eligible preference wins on fresh login when no explicit destination exists; a single eligible namespace is automatic; several without a valid preference show the chooser. A preference change does not switch the active tab.

Source inspection establishes code shape, not runtime correctness. The virtual namespace feature is opt-in through `VIRTUAL_NAMESPACES_ENABLED`; integration must use an environment with the flag, migrations and at least two ready namespaces. The frontend must still handle no-access, pending and failed entries.

## Concrete frontend integration points

- `app/src/views/private/components/project-info.vue`: header selector and two-level label. Keep the project identity; selector only emits switch intent.
- `app/src/views/private/components/module-bar.vue`, `app/src/router.ts`, `app/src/views/private/private-view.vue`: native rail entry and protected/static platform routes. Global Administration must be separate from the regular User Directory.
- `app/src/auth.ts`, `app/src/api.ts`, app stores/router guards: one active-namespace context, token and refresh serialization, origin-bound retries, protected bootstrap, request ledger and reset hooks. Do not implement these a second time inside C1/C7.
- `app/src/modules/users/routes/collection.vue`, `components/navigation.vue`, `routes/item.vue`, invite component: retain the native directory presentation while separating global-account operations from child-membership operations. A local member API must never feed a shared-user editor that writes `/users`.
- Existing Content, Files, Settings and right-sidebar components: keep the current modules and register their reads, uploads, polling, selections, dialogs, cached schema/permissions and manual actions with the shared switch lifecycle. Use the [capability matrix](frontend-capability-coverage.md) as the per-surface closure list.

The old `codex/virtual-namespaces-frontend` integration branch is a **design/prototype reference only** until rebased and audited against these contracts. Its mock routes, separate child home and custom directory/card pages do not count as this plan's live implementation. Reuse isolated coordinator code only after checking its request lifecycle and ability to host the native Directus modules.

## Backend handoff to settle before promising the complete feature

1. **D04:** Make Global Admin effective app access unambiguous without a child membership; provide examples for Global Admin with and without a child role. Distinguish local-admin authority from platform authority on every relevant endpoint.
2. **D05/D09/D07:** Enforce child-only user reads; supply the local directory projection/actions needed for the native UI. Define safe File Library, asset and local Settings reads/writes instead of broad reads plus blocked writes. Keep local role/schema/flow management.
3. **D06:** Choose namespace creation semantics: empty child versus importing an existing area. Expose Global Admin-only list/create/status (and only agreed edit/delete actions), validation, readiness, idempotency and failure recovery. The frontend can preserve native selection controls without claiming unsupported mutations.
4. **D14:** Supply platform user/role/membership projections and distinct counts, with server-side namespace/role filtering. Supply one user's complete membership projection, cross-namespace role choices and authorized add/change/remove for the native Global Admin profile, alongside global create/invite with zero-to-many initial role assignments or a recoverable transaction, including existing-email and invitation ordering rules.
5. **Self-profile/default preference:** Supply a safe native self-profile read/write contract for personal fields without child access to the shared directory, plus a persisted, server-validated default virtual namespace preference editable by its owner (and by Global Admin for another user). Define zero/one/many eligible choices, revocation/unready handling, explicit deep-link precedence and Global Admin fallback. This is distinct from the server's `VIRTUAL_NAMESPACES_DEFAULT`.
6. **D03/D07/D08/D11:** Verify two-tab refresh/cookie/asset behavior, shares, async jobs and relations against the actual backend, not just DTOs. Keep the user on a safe static state when access is lost while preserving a valid login.

No frontend application files are changed by this planning document. Implementation starts only after this plan is reviewed and the first slice is selected.
